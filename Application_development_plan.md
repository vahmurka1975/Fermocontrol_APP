# План развития приложения «ФермоКонтроль»

**Файл:** `Application_development_plan.md`  
**Дата:** 29 октября 2026 года  
**Статус:** проект плана для согласования и пошаговой реализации  
**Репозиторий:** https://github.com/vahmurka1975/Fermocontrol_APP  
**Основная ветка:** `main`  
**Платформа:** Android; Kotlin и Jetpack Compose.

## Назначение и границы плана

Создать удобный офлайн-журнал домашнего сыровяления: продукты, взвешивания, наблюдения, условия, фотографии, напоминания и архив результатов. Первую полноценную версию ориентировать на мясные продукты. Другие направления ферментации добавлять позднее отдельными профилями.

Первым организовать обновление приложения по воздуху для проверки на настоящем смартфоне. Затем обеспечить надёжное хранение и резервное копирование на Яндекс Диск или Google Диск по выбору пользователя. После этого последовательно расширять ежедневные функции.

План задаёт целевое поведение. Наличие готовых функций в текущем Android-проекте необходимо подтвердить проверкой исходников и запуском. HTML-прототип служит ориентиром интерфейса и логики, но не подтверждает реализацию этих возможностей в Android.

Приложение фиксирует процесс, но не подтверждает пищевую безопасность продукта по весу, запаху или фотографии. Достижение целевой потери веса не означает автоматической готовности к употреблению.

## Основные принципы

- Работа с журналом без обязательной регистрации и без интернета.
- Сохранность данных при обновлениях и изменениях структуры базы.
- Небольшие проверяемые выпуски вместо крупного непроверенного обновления.
- Понятное различие между резервным копированием и синхронизацией устройств.
- Минимум повторного ввода; основное ежедневное действие — «Взвесить».
- Секреты, ключи подписи и пользовательские данные не попадают в Git.
- Ошибки облака, уведомлений или датчиков не блокируют основной журнал.

# 1. Организовать обновления по воздуху и тестирование на смартфоне

## 1.1. Что реализуем

Обновления по воздуху реализуемы: новую сборку можно скачать на смартфон через интернет и установить поверх предыдущей без кабеля и Android Studio. Для первого этапа достаточно подписанного APK в GitHub Releases. Позднее приложение сможет само проверять наличие нового выпуска и предлагать установку.

Это не скрытая установка: пользователь подтверждает обновление в системном интерфейсе Android. Для установки APK может понадобиться разрешение для источника, из которого запускается установщик. Способ зависит от версии Android и выбранного механизма установки.

Нативные функции Kotlin и Compose обновляются новым APK, а не незаметной подменой HTML или исполняемого кода.

## 1.2. Проверить исходное состояние

1. Записать модель смартфона и версию Android.
2. Выяснить, установлено ли приложение и каким способом: Android Studio или APK.
3. Проверить фактический `applicationId`, номер версии и используемую подпись.
4. Убедиться, что текущие данные можно экспортировать и восстановить.
5. Выбрать, будет ли существующая установка продолжена или потребуется разовый перенос в новую подписанную сборку.

**Важно:** сборка с другим ключом подписи обычно не устанавливается поверх прежней с тем же идентификатором. Нельзя предлагать удаление приложения до создания и проверки копии данных. При необходимости перехода использовать экспорт/импорт либо отдельный идентификатор тестовой сборки.

## 1.3. Настроить постоянную подпись

1. Создать постоянный ключ подписи для выбранного канала распространения.
2. Сохранить защищённые резервные экземпляры ключа вне репозитория.
3. Зафиксировать название alias и порядок восстановления доступа.
4. Исключить keystore, пароли и локальные настройки подписи через `.gitignore`.
5. Для автоматической сборки использовать защищённые секреты репозитория, а не файлы в Git.
6. Ограничить доступ к секретам и не выводить их в журналы сборки.

Для обычного обновления должны сохраняться совместимая подпись и идентификатор приложения; `versionCode` нового выпуска должен увеличиваться. Потеря ключа при прямом распространении APK может лишить возможности обновлять существующие установки.

## 1.4. Наладить выпуск APK

1. Проверить сборку проекта на чистом окружении.
2. Настроить GitHub Actions: проверки, тесты и сборка подписанного APK.
3. Начать с ручного запуска публикации или явно созданного тега, а не публикации каждого коммита.
4. При ошибках тестов или сборки не публиковать выпуск.
5. Прикреплять к GitHub Release APK и контрольную сумму SHA-256.
6. Указывать версию, дату, изменения, сценарий проверки и известные ограничения.
7. Разделять тестовые и стабильные выпуски. По умолчанию не предлагать тестовые сборки пользователям стабильного канала.

Для публичного репозитория доступ к файлам выпуска организовать без секретов в APK. Если репозиторий или файлы станут приватными, отдельно спроектировать авторизованную доставку. Общий GitHub-токен запрещено встраивать в приложение.

## 1.5. Провести первое обновление вручную

1. Установить базовую подписанную версию на телефон.
2. Создать контрольный продукт, несколько взвешиваний и архивную запись.
3. Выпустить следующую сборку с большим `versionCode`.
4. Скачать APK на смартфоне и подтвердить обновление поверх установленной версии.
5. Проверить сохранность записей, настроек и работоспособность приложения.
6. Записать результаты и сделать этот сценарий обязательной проверкой будущих выпусков.

Этот вариант уже является обновлением по воздуху. Встроенная проверка обновлений не должна задерживать начало реального тестирования.

## 1.6. Добавить проверку обновлений в приложение

1. Разместить доступные приложению метаданные выпуска: код и имя версии, минимальные требования, URL APK, размер и контрольную сумму.
2. Добавить экран «О приложении» с текущей версией и кнопкой «Проверить обновления».
3. Показывать описание подходящего выпуска и действия «Скачать» / «Позже».
4. Загружать по HTTPS; обрабатывать нехватку места, обрыв связи и повторную попытку.
5. Проверять целостность файла, ожидаемый пакет и подпись доступными средствами Android. Контрольная сумма сама по себе не заменяет доверенную подпись.
6. Открывать системный установщик безопасным способом, без публичного доступа к локальным файлам.
7. Не предлагать откат на меньший `versionCode` как обычное обновление.
8. Показывать результат проверки и не мешать работе при недоступности сервера.

**Критерий завершения:** минимум два последовательных выпуска установлены на настоящем смартфоне без кабеля, удалений приложения и потери контрольных данных; рабочий ключ защищён и зарезервирован.

# 2. Проверить основу приложения и закрепить предметную модель

**Цель:** понять фактическое состояние Android-проекта и подготовить изменения без потери существующего журнала.

1. Проверить сборку, зависимости, экраны, способ хранения, экспорт и тесты.
2. Сопоставить Android-реализацию с HTML-прототипом и согласованными требованиями.
3. Составить перечень: реализовано, частично, отсутствует, требует исправления.
4. Зафиксировать навигацию: активные продукты, архив, карточка, добавление, настройки.
5. Разделить интерфейс, бизнес-логику, хранение и внешние интеграции без избыточного усложнения.
6. Установить порядок обработки ошибок и отображения состояния операций.

## Правила продукта

- Использовать название «Продукт», а не «Партия».
- Номер назначать автоматически: первый свободный среди активных продуктов.
- После извлечения переносить продукт в архив и освобождать номер.
- Постоянный идентификатор продукта не связывать с его видимым номером.
- Исходные параметры не изменять обычной кнопкой «Редактировать».
- Добавление измерения выполнять действием «Взвесить».
- Дату и время измерения фиксировать автоматически.
- Основу, специи, оболочку и наблюдения выбирать из справочников.
- Архив сохраняет историю, состав, фотографии и итоговые показатели.

Отдельно согласовать исправление ошибок ввода: корректировка взвешивания не должна незаметно менять исходные параметры продукта. Удаление или исправление важных записей должно быть явным и защищённым от случайного нажатия.

**Критерий завершения:** есть проверенная карта текущих возможностей, согласованные правила данных и воспроизводимая сборка.

# 3. Обеспечить надёжное локальное хранение

**Цель:** журнал сохраняется при перезапуске, обновлении и изменении структуры приложения.

1. Спроектировать базу Room: продукты, взвешивания, наблюдения, справочники и связи.
2. Предусмотреть расширение для фотографий, этапов, рецептов и условий.
3. Хранить постоянные идентификаторы, единицы измерения и временные отметки.
4. Отделить архивный статус от физического удаления.
5. Если используется JSON, реализовать проверяемый перенос в Room.
6. Перед переносом сохранить исходный файл; при ошибке не уничтожать его.
7. Добавить тесты миграций и расчётов; не использовать разрушительную пересоздачу базы в рабочих сборках.
8. Сделать версионированный локальный экспорт и импорт.
9. Определить хранение изображений: файлы приложения и ссылки из базы, а не случайные внешние пути.

## Обязательные проверки

- Начальный вес положителен; текущий вес корректно проверяется.
- Процент потери считается от исходного веса, округление выполняется для отображения.
- Прибавка массы отображается корректно, а не обрезается до нуля.
- Повторное использование номера не объединяет разные продукты.
- Перезапуск и обновление не меняют значения и порядок событий.
- Повреждённый импорт не заменяет рабочую базу частично.

**Критерий завершения:** контрольный журнал проходит перенос, экспорт/импорт и обновление без потерь; ошибочная операция не разрушает текущие данные.

# 4. Реализовать резервные копии на Яндекс Диск и Google Диск

**Цель:** восстановить журнал после потери телефона или переустановки приложения.

## 4.1. Пользовательские настройки

Предлагаемый вариант для согласования: один активный облачный сервис на выбор, ежедневная копия при наличии изменений, Wi-Fi по умолчанию, последние 10 успешных копий. Ручная копия доступна всегда. Это настройки приложения, а не ограничения облачных сервисов.

Экран «Данные → Резервное копирование» должен содержать выбор сервиса, подключение/отключение аккаунта, ручное создание, параметры автоматического копирования, дату последнего успеха, статус несохранённых изменений и восстановление.

## 4.2. Последовательность реализации

1. Спроектировать единый интерфейс облачного хранилища и отдельные адаптеры сервисов.
2. Подключить официальную авторизацию Яндекса, затем Google либо в обратном порядке.
3. Запрашивать минимально необходимые разрешения; проверить настройки доступа и регистрации приложений для каждого провайдера.
4. Надёжно хранить токены на устройстве; не включать их в резервные копии и логи.
5. Создавать согласованный снимок данных, не копировать открытую SQLite-базу простым чтением одного файла.
6. Формировать архив с манифестом: версия формата, версия приложения, время, число записей и контрольные суммы.
7. Загружать новую копию, проверять результат и только затем применять ротацию старых.
8. Реализовать фоновые задачи, ограничения сети и повторные попытки.
9. Показывать понятные ошибки: доступ отозван, мало места, нет сети, файл повреждён.
10. Проверить полный цикл отдельно на Яндекс Диске и Google Диске.

Android может задерживать фоновую работу из-за энергосбережения. Не обещать запуск строго в заданную минуту и не показывать успех до подтверждения загрузки.

## 4.3. Содержимое и защита копии

Включать активные и архивные продукты, измерения, наблюдения, справочники, настройки, фотографии и остальные добавляемые сущности. Не включать ключи подписи, токены, пароли и временные загрузки APK.

Если добавляется шифрование копии, ключ должен быть восстанавливаем на новом телефоне пользователем. Единственный ключ из Android Keystore старого устройства не подходит для переносимой резервной копии. Отдельно согласовать пароль, восстановление доступа и предупреждение о невозможности расшифровки без ключа.

## 4.4. Восстановление

1. Получить список копий выбранного аккаунта.
2. Проверить версию формата, целостность и доступное место.
3. Показать дату, количество продуктов, измерений и фотографий.
4. Предупредить, что на первом этапе восстановление заменяет журнал, а не объединяет его.
5. Создать локальную копию текущего состояния.
6. Подготовить и проверить восстановленные данные во временном месте.
7. Заменить данные согласованно; не оставлять половину старой и половину новой базы.
8. Повторно зарегистрировать напоминания и запросить необходимые системные разрешения.

**Критерий завершения:** на чистой установке журнал полностью восстановлен из каждого облака; отмена, повреждённый архив и обрыв связи не портят текущие данные.

# 5. Сделать удобный ежедневный контроль

**Цель:** при открытии приложения понятно, какие продукты требуют внимания.

1. Показать активные продукты: номер, название, возраст, последний вес, потеря массы и дата взвешивания.
2. Добавить блок «Сегодня»: пора взвесить, измерение просрочено, достигнута цель.
3. Реализовать поиск, сортировку и фильтры без потери выбранного режима.
4. Сделать карточку: «Обзор», «Журнал», «График», «Фото».
5. Оставить «Взвесить» главным действием.
6. Предлагать прежние наблюдения как значения по умолчанию с явным подтверждением актуальности.
7. Защитить от повторного сохранения при двойном нажатии.
8. Архивировать с подтверждением, сохраняя все данные и освобождая номер.
9. Отделить плановую архивацию от удаления и задать безопасные правила восстановления из архива.

При возвращении архивного продукта в активные назначать свободный номер, если прежний уже занят; постоянный идентификатор не меняется.

**Критерий завершения:** продукт создаётся, взвешивается и архивируется без лишнего ввода; повторное использование номера не смешивает историю.

# 6. Настроить напоминания, графики и фотографии

## 6.1. Напоминания

1. Назначать интервал взвешивания каждому продукту; предусмотреть общее значение по умолчанию.
2. После нового взвешивания пересчитывать следующую дату проверки.
3. Добавить напоминания о действиях: перевернуть, осмотреть, перенести, начать следующий этап.
4. Позволить отложить или отключить отдельное напоминание.
5. По нажатию уведомления открывать нужный продукт.
6. Отменять будущие напоминания после архивации.
7. Обрабатывать отказ в разрешениях, перезагрузку телефона и восстановление резервной копии.
8. Показывать задачи внутри приложения, даже когда системные уведомления отключены.

Не обещать точное время доставки обычных фоновых уведомлений. Применять механизмы Android сообразно задаче; не запрашивать специальные разрешения на точные будильники без необходимости.

## 6.2. Графики

1. Отображать массу и процент потери относительно исходного веса.
2. Показывать целевую линию и точные значения выбранного измерения.
3. Учитывать несколько записей за день и реальные интервалы между ними.
4. Отмечать этапы процесса и значимые наблюдения.
5. Корректно обрабатывать отсутствие данных, одно измерение и временное увеличение веса.
6. Позднее добавить приблизительный прогноз достижения цели с указанием ограничений.

Формула потери веса: `(исходный вес − текущий вес) / исходный вес × 100%`. Исходный вес должен быть положительным. Не скрывать отрицательную потерю, если вес увеличился: показать значение и предложить проверить ввод.

## 6.3. Фотографии

1. Добавлять фото при создании продукта и к записи журнала.
2. Поддержать камеру и системный выбор изображения.
3. Копировать выбранные изображения в управляемое приложением хранилище, чтобы удаление исходника из галереи не разрушало журнал.
4. Сохранять дату, подпись и связь с записью.
5. Создавать уменьшенные изображения для списка; согласовать качество и расход памяти.
6. Обрабатывать отмену выбора, недостаток места и отсутствие доступа.
7. Включать фотографии в резервные копии и проверять восстановление связей.

**Критерий завершения:** напоминание ведёт к нужному действию, график соответствует журналу, фотографии сохраняются после перезапуска и восстановления на новом устройстве.

# 7. Добавить этапы процесса

**Цель:** хранить последовательность действий, не переписывая исходную карточку продукта.

1. Согласовать базовые этапы: посол, ферментация, сушка, выравнивание и пользовательские варианты.
2. Записывать начало и завершение этапа как отдельные события.
3. Добавить заметки и плановые действия для каждого этапа.
4. Поддержать ручное завершение и переход с подтверждением.
5. Отображать этапы на временной шкале и графиках.
6. Сохранять историю исправлений дат и названий этапов.
7. Включить этапы в экспорт и резервные копии.

Достижение заданного веса или истечение времени может создавать подсказку, но не должно автоматически подтверждать безопасность продукта или завершать процесс без согласованного правила.

**Критерий завершения:** история показывает, когда и на каком этапе находился продукт; изменение текущего этапа не уничтожает предыдущие события.

# 8. Добавить места хранения и журнал условий

**Цель:** понимать, в каких условиях находился каждый продукт.

1. Создать справочник мест: камера, холодильник, помещение и пользовательские названия.
2. Записывать перемещения продукта с датой и временем.
3. Хранить температуру и влажность как измерения места, а не только как поля взвешивания.
4. Сопоставлять показания с продуктами по интервалам нахождения в этом месте.
5. Настраивать целевые диапазоны по месту или этапу; различать пользовательскую настройку и фактическое измерение.
6. Показывать выход за диапазон и отсутствие свежих данных как разные состояния.
7. Добавить ручной ввод pH и активности воды `aw`, если есть соответствующие измерительные приборы.
8. Записывать единицы, время и источник измерения; не подменять измеренное значение расчётной оценкой.
9. Включить места, перемещения и условия в копирование и восстановление.

Нельзя считать, что единственное старое измерение описывает условия до настоящего времени. Пропуски должны быть видны.

**Критерий завершения:** можно сопоставить продукт и условия за выбранный период без многократного ввода одинаковых показаний для каждой карточки.

# 9. Добавить рецепты и повторение удачных результатов

**Цель:** создавать новые продукты без повторного заполнения одинаковых данных.

1. Собственные рецепты и шаблоны.
2. Ингредиенты с количеством и единицами измерения.
3. Пересчёт состава на другой исходный вес.
4. Шаблоны этапов и напоминаний.
5. Создание продукта по рецепту.
6. Создание нового продукта на основе архивного.
7. Оценка результата: вкус, аромат, плотность, солёность и заметка «Что изменить».
8. Поиск и группировка рецептов, сохранение вариантов.

При создании продукта сохранять снимок использованного рецепта. Последующее редактирование рецепта не должно менять состав старых продуктов.

Калькуляторы специализированных посолочных компонентов выносить в отдельную задачу. Нельзя считать разные смеси взаимозаменяемыми: нужны точный состав, концентрации, единицы и проверенная методика. Не включать такой калькулятор только ради сходства с конкурентами.

**Критерий завершения:** из удачного архивного продукта можно создать новый с нужным составом и настройками, но без переноса прежних измерений и фотографий как новой истории.

# 10. Добавить отчёты, сравнение и работу с архивом

**Цель:** использовать накопленные данные для следующих продуктов.

1. Расширить поиск и фильтры архива.
2. Сформировать PDF-карточку продукта: состав, этапы, вес, график, наблюдения, выбранные фото и оценка.
3. Добавить расширенный CSV-экспорт с понятными единицами и кодировкой.
4. Сравнивать несколько продуктов по графикам и итоговым показателям.
5. Группировать результаты по рецептам и другим выбранным параметрам.
6. Поддержать пакетный экспорт выбранных записей.
7. Проверить экспорт больших журналов и корректное отображение кириллицы.

Для сравнения графиков предусмотреть выравнивание по дням от начала процесса, а не только по календарной дате. В отчётах указывать исходные единицы и пропуски измерений.

Различать наблюдение и доказанную причину: совпадение более быстрой сушки с определённой оболочкой ещё не доказывает причинную связь.

**Критерий завершения:** историю продукта можно понять вне приложения, а несколько результатов сопоставить без ручного переноса данных.

# 11. Подготовить первую стабильную версию

Проверки выполнять после каждого обновления. На этом этапе провести полный контроль и зафиксировать стабильный выпуск.

1. Пройти полный сценарий на настоящем смартфоне: создание → измерения → напоминания → архив → копирование → восстановление.
2. Проверить обновления с поддерживаемых предыдущих версий.
3. Проверить миграции базы и совместимость старых резервных копий.
4. Проверить отсутствие сети, отзыв разрешений, заполнение памяти и прерывание операций.
5. Проверить большой журнал и большое количество фото.
6. Проверить крупный шрифт, тёмную тему и небольшие экраны.
7. Проверить доступность элементов, контраст и понятные подписи.
8. Подготовить краткую справку, описание хранения данных и порядок восстановления.
9. Удалить отладочные журналы с персональными данными, проверить экспорт и диагностические сообщения.
10. Зафиксировать версию, список изменений и известные ограничения.

Возврат к старому APK не считать надёжным откатом: старая версия может не понимать обновлённую базу, а Android может не разрешить обычное понижение версии. Основной путь — исправляющее обновление и проверенная резервная копия.

**Критерий завершения:** стабильный выпуск устанавливается и обновляется без ручного вмешательства в файлы и базу, а пользователь может восстановить журнал на новом устройстве.

# 12. Дальнейшее развитие: несколько устройств и датчики

## 12.1. Полноценная синхронизация

1. Определить модель аккаунта и хранения общей истории.
2. Идентифицировать устройства и каждое изменение.
3. Учитывать удаления, работу без интернета и повторную доставку операций.
4. Согласовать правила конфликтов: одновременное исправление, удаление и изменение одной записи.
5. Синхронизировать фотографии без потери связей и лишнего дублирования.
6. Показывать состояние обмена и нерешённые конфликты.
7. Проверить разрыв связи на каждом этапе.

Не подменять синхронизацию постоянным восстановлением облачной копии: это может уничтожить изменения другого устройства.

## 12.2. Датчики температуры и влажности

1. Выбрать конкретную модель и проверить доступность протокола.
2. Реализовать подключение и необходимые разрешения.
3. Сохранять показания с временем, единицами и идентификатором источник.
4. Обрабатывать разрывы связи, дублирование и рассинхронизацию времени.
5. Отмечать пропуски и устаревшие данные.
6. Добавить предупреждения по пользовательским диапазонам.
7. Проверить автономность смартфона и устойчивость фонового сбора.

## 12.3. Весы

1. Выбрать поддерживаемую модель.
2. Показать полученное значение и единицы.
3. Проверять стабильность показаний, если протокол предоставляет такой признак.
4. Сохранять результат после подтверждения пользователя.
5. Предусмотреть ручной ввод при отсутствии связи.

Управление климатической камерой — отдельный проект по ответственности и надёжности. Его не объединять с первым подключением датчиков.

# 13. Организация работы и выпусков

## 13.1. Цикл одного небольшого блока

1. Описать пользовательский сценарий и критерии готовности.
2. Проверить текущий код и зависимости задачи.
3. Внести изменения и тесты.
4. Проверить сборку и сохранность данных.
5. Опубликовать подписанный тестовый выпуск.
6. Установить обновление по воздуху на смартфон.
7. Пройти короткий проверочный сценарий.
8. Исправить замечания.
9. Зафиксировать результат в Git и перейти к следующей задаче.

## 13.2. Содержание описания выпуска

- Версия и дата.
- Что нового.
- Что проверить на смартфоне.
- Известные ограничения.
- Меняется ли формат данных.
- Требуется ли предварительная резервная копия.

## 13.3. Условия готовности задачи

- Реализован заявленный сценарий, а не только экран.
- Обработаны отмена, ошибка ввода и повторное нажатие.
- Старые данные не теряются.
- Есть проверяемый сценарий приёмки.
- Обновлены резервное копирование и экспорт, если появились новые сущности.
- В коммит не попали ключи, токены, локальные пути и персональные данные.
- Выпуск проверен на настоящем смартфоне.

# 14. Приоритеты и зависимости

| Очередь | Этапы | Результат |
|---|---|---|
| Первая | 1–4: обновления, проверка основы, надёжное хранение, оба облака | Можно тестировать на смартфоне и восстанавливать журнал |
| Вторая | 5–6: ежедневный контроль, напоминания, графики и фотографии | Удобная повседневная работа |
| Третья | 7–9: этапы, условия и рецепты | Полная история и повторение результатов |
| Четвёртая | 10–11: отчёты, сравнение и стабилизация | Первая законченная стабильная версия |
| Последующая | 12: синхронизация, датчики и весы | Несколько устройств и автоматизация |

После добавления каждой новой сущности расширять формат копии и тесты восстановления. Не откладывать поддержку новых данных в резервных копиях до последнего этапа.

Сроки и номера версий назначать после проверки текущего кода и оценки конкретного блока. В этом плане они намеренно не привязаны к неподтверждённым датам.

# 15. Решения, которые нужно подтвердить перед реализацией

1. Модель смартфона, версия Android и способ установки текущей сборки.
2. Сохраняем ли совместимость с установленной тестовой сборкой или отдельно устанавливаем первый постоянно подписанный вариант.
3. Доступность репозитория и допустимый круг получателей APK.
4. Первый канал доставки: подписанные APK в GitHub Releases; встроенная проверка обновлений — следующим небольшим блоком.
5. Активно одно облако на выбор, без обязательного аккаунта для обычного ведения журнала.
6. Предлагаемая политика копий: ежедневно при изменениях, по умолчанию Wi-Fi, последние 10 успешных копий, ручной запуск в любой момент.
7. Требуется ли шифрование переносимого архива и как пользователь восстанавливает ключ.
8. Первая предметная область — мясное сыровяление; расширения добавляются отдельными профилями.

# 16. Ближайший рабочий шаг

Подготовить постоянную подпись, канал тестовых выпусков и проверить первое обновление поверх установленной версии без потери данных.

Начать с проверки фактического Android-проекта и сведений о смартфоне. Затем выпустить две последовательные подписанные сборки и пройти установку второй поверх первой через интернет. Только после успешной проверки этого сценария расширять функциональность.

Ключи подписи и пароли в чат или репозиторий не передавать.
